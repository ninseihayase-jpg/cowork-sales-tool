# 商談情報クエリツール 設計書（ドラフト）

商談（`deals`）を中心に、SFA内のデータを様々な切り口で横断集計・出力できるツール。
本書は**ドラフト**。§6の論点をユーザーと合意してから実装フェーズへ進む
（この設計書の完成が最初のマイルストン）。

- リポジトリはPUBLIC。**認証情報・クライアント名・実データは本書に書かない**。

## 1. ゴール・非スコープ

**ゴール**: 「〇〇業界×失注理由の内訳」「担当者別・ステージ別のパイプライン金額」
「展示会別の受注率」のような、あらかじめページを作っていない切り口の集計を、
コードを書かずにその場で作れるようにする。

**非スコープ（当面）**:
- 書き込み（登録/編集/削除）はこのツールの対象外。**読み取り専用**に限定する。
- `/weekly-numbers`・`/weekly-numbers/audit`・既存の各種一覧ページの置き換えではない
  （あちらは「定義が固まった定型指標」、本ツールは「その場の自由な深掘り」という棲み分け）。
- 全社への公開・Hisho側ダッシュボードへの組み込みは今回は考えない（SFA内の一機能）。

## 2. 想定ユースケース（たたき台）

- 業界×ステージのクロス集計（どの業界がどのフェーズで滞留しているか）
- 担当者別・四半期別のパイプライン金額推移
- 失注理由(`close_reason`)の内訳と、業種/リード経路(`lead_pattern`)別のクロス
- 展示会(`exhibition_name`)別の商談化率・受注率
- 「次回MSが〇日以上更新されていない商談」のような放置検知
- 論点(`deal_issues`)が多い商談の傾向（業種・金額帯との相関）
- 特定条件（例: 開発案件あり×金額〇万円以上×担当A）での商談リストをCSVに出す

いずれも「毎回コードで新しいページを書く」には割に合わない一過性の深掘りが中心、
という理解で設計している（違えば§6で訂正してほしい）。

## 3. アーキテクチャの分岐点（最大の論点）

出力方式の入口をどう作るかで実装規模が大きく変わる。3案を比較する。

### 案A: 生SQL（SELECT限定）を直接書ける画面
テキストエリアにSQLを書いて実行→結果テーブル表示・CSV出力。
- 長所: 最も自由度が高い。JOIN・サブクエリ・集計関数など、思いつく切り口を素早く試せる。
  実装も軽い（クエリの妥当性はSQLite自身に任せられる）。
- 短所: SQLが書ける前提になる。テーブル名・列名を覚えている必要がある
  （スキーマ一覧の補助表示は要る）。

### 案B: GUIクエリビルダー
対象テーブル・表示列・絞り込み条件・グループ化をプルダウン/チェックボックスで組み立て、
裏でSQLを生成する（ノーコード）。
- 長所: SQL知識が不要。誤入力によるエラーが起きにくい。
- 短所: 実装コストが重い（JOINの選び方・集計関数の組み合わせをUIでどこまで表現するか
  は設計が難しく、結局「複雑な切り口には対応できないビルダー」になりがち）。

### 案C: 段階導入（案Aを先に作り、頻出パターンをボタン化）
まず案AでSELECT専用の実行画面を作る。実際に書いたクエリの中でよく使う切り口が
見えてきたら、それを「保存済みレポート」としてワンクリック実行できるようにする
（パラメータ化: 期間・担当者などだけ差し替え可能にする）。
- 長所: 最小の実装でまず使い始められ、本当に必要なUIが後から分かる。
  既存の`weekly_numbers_audit_page`（定義＋値＋元データを表示する監査ページ）は
  実質「案Cの保存済みレポート」を先取りした前例で、様式を流用できる。
- 短所: 初期はSQLを書ける人（早瀬）専用になる。

**現時点のたたき台としては案C（生SQLで最小実装→よく使う切り口をテンプレ化）を推奨**。
理由: このツールの利用者は当面ユーザー自身が主で、GUIビルダーの学習コストに見合う
利用者数がまだいない一方、案Aは今日のニーズにすぐ応えられ、案Bへの拡張余地
（保存済みクエリのパラメータ化）も自然に残せるため。§6で確認したい。

## 4. データモデル・対象範囲

`deals`を中心に、以下のテーブルとの結合を主に想定する（`sfa_db.py`のSCHEMA参照）。

| テーブル | 関係 | 主な用途 |
|---|---|---|
| `accounts` | `deals.account_id` | 業界・会社規模での絞り込み |
| `activities` | `activities.deal_id` | 面談回数・直近接点日 |
| `deal_milestones` | `deal_milestones.deal_id` | 次回MS関連の深掘り |
| `deal_issues` | `deal_issues.deal_id` | 論点の有無・件数 |
| `dev_projects` | `dev_projects.deal_id` | 開発案件との掛け合わせ |
| `leads` | `leads.deal_id` | リード化後に紐づいた商談との関係 |

商談テーブル自体の主な列: `stage`/`business_type_l1・l2`/`lead_pattern`/`owner`/
`value_lumpsum`系3種/`status`/`close_reason`/`next_milestone_date`/`exhibition_name`等
（詳細は`cowork/sfa_db.py`の`CREATE TABLE deals`参照）。

## 5. 安全性のガードレール

読み取り専用と言っても、実行画面である以上は事故防止を作り込む。

1. **接続レベルでの強制読み取り専用**: SQLiteのURI接続 `file:...?mode=ro` で開く
   （文字列の先頭が`SELECT`かどうかのチェックだけでは、コメントや複文
   （`; DELETE ...`）で回避され得るため不十分）。
   Hisho側の`/api/execute`（`INSERT/UPDATE/DELETE/SELECT`を許し、判定も先頭語チェックのみ）
   は同種の内部APIとして参考になるが、**書き込み可・判定が弱いという点ではむしろ
   反面教師**として扱い、本ツールはより厳格にする。
2. **タイムアウト/行数上限**: 巨大な直積JOIN等で固まらないよう、実行時間の上限
   （例: 5秒）と返却行数の上限（例: 1000行、超過分は「他N件省略」表示）を設ける。
3. **認証**: 既存のBasic認証/セッション認証（`/login`）をそのまま使う。
   このツール専用の権限分離（誰なら実行できるか）は今のところ存在しない
   （SFA全体が共通ログインのため）。§6で範囲を確認したい。
4. **監査**: 誰が・いつ・何を実行したかを軽く記録する（`query_log`テーブル等）。
   クライアント名を含むクエリ文字列自体は本書のような公開ドキュメントには一切出さない
   （DBにのみ保持）。

## 6. 論点（要ユーザー判断）— この設計書のたたき台に対する主な分岐点

1. **入力方式**: §3の案A/B/Cのどれで進めるか（推奨は案C＝まず生SQL）。
2. **対象範囲**: `deals`中心という理解で合っているか。開発案件(`dev_projects`)・
   タスク(`tasks`)・論点(`deal_issues`)まで含めた「SFA全体のクエリツール」を
   最初から想定するか、まず商談まわりに絞るか。
3. **利用者**: 実質ユーザー自身のみを想定しているか、他メンバーにも将来的に
   開放する前提を最初から作っておくか（§5.3の権限設計に影響）。
4. **保存・共有**: 都度書き捨てでよいか、お気に入り/テンプレとして保存したいか
   （保存するなら§3案Cの「パラメータ化」まで見据えて設計する）。
5. **出力形式**: 画面テーブル表示だけで十分か、CSV/Excelダウンロードも初手から要るか。

以上を合意でき次第、§3で決めた案に沿ってフェーズ計画（データ基盤→実行画面→
テンプレ化）を追記し、実装に進む。
