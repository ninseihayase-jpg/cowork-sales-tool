# 直近タスク設計（簡素化版）機能 設計構想

**ステータス**: ①設計doc — **確定**（2026-10-06、全論点ユーザー確認済み）
**作成日**: 2026-10-06
**関連**: 既存「直近タスク設計」機能（issue #101、`/tasks/daily-plan`）とは別の新機能として併存

## 1. 背景・目的

現行の「直近タスク設計」（`cowork/webapp.py:13048-13727`、約750-800行）は、時間軸（6:00-21:00、
15分刻み）付きの縦型カレンダーに、選択したタスクをドラッグ&ドロップで配置する機能。Googleカレンダー
連携（1名限定）・工数キャパシティ管理（`/tasks/capacity`）を含む高機能だが、ユーザーより
「簡素化して簡単に使えるようにしたい」との要望。

新しい仕様では、**時間軸（時刻単位の精緻な配置）を廃止**し、**曜日単位（月〜金のどの日にやるか）
の粗い粒度**に落とし込む。代わりに「テーマ」という軸を導入し、各テーマの直近マイルストンと、
今週やりたいタスクを一体で管理・出力する。

**「テーマ」の定義（2026-10-06、ユーザー指摘により訂正）**: テーマ＝新規の概念ではなく、
**既存のタスク紐づけ機能（`/tasks`看板の「Delivery/商談/社内PJ」チップ群）がすでに持っている
分類・グルーピングをそのまま使う**。具体的にはタスクが持つ`link_type`/`link_id`
（紐づく先がDelivery・商談(Deal)・社内PJ(Issue)のどれで、どの行か）そのものがテーマの実体。
`tasks.project`（`task_projects`マスタ）は全くの別概念であり、本機能では使わない
（詳細は §3.1 参照）。

### 最終的に欲しい2つのアウトプット

**Output1（Slackメモ形式）**: テーマが1階層目（次のマイルストンを併記）、今週やりたいタスクが
2階層目の箇条書き。Slackに貼り付けるとそのまま箇条書きとして認識される書式（`•`/`◦` 等の
Unicode文字、Markdown記法ではない）。実例（ユーザー提供のSlackキャプチャより）:

```
Delivery
• A社案件 - 10/8先方担当者名
  ◦ 納品物最終化
  ◦ 報告資料Update
• A社タブレット - 10/13中間報告リスケ
  ◦ リスケ方針固め→連絡
...
営業
• B社 - 10/5本店向け資料
...
```
（"Delivery"/"営業"/"経企"/"マーケ"/"営業企画" がテーマの「大分類」、
"A社案件 - 10/8先方担当者名" のようにテーマ名+直近マイルストンを1行で表した行がテーマ本体、
その下のタスクが今週やりたい作業。※社名・個人名は社外秘のため本docでは全て仮名に置換）

**注（2026-10-06訂正）**: このSlackキャプチャは手書きメモであり、大分類ラベル
（"営業"/"経企"/"マーケ"/"営業企画"）はユーザー自身の手による簡略表記。本機能が自動生成する
Output1では、§3.1で確定した**既存看板と同じバケット名**（"Delivery"/"商談"/
"社内PJ(経営企画)"/"社内PJ(マーケ)"等）をそのまま使う（"営業"ではなく"商談"、
"経企"ではなく"社内PJ(経営企画)"という表記になる）。既存の分類をそのまま流用する方針
（ユーザー確定済み）を優先し、Slackキャプチャの見た目に独自の短縮ラベルを追加することはしない。

**Output2（日別タスク表）**: テーマを縦に並べ、月〜金を横に並べた表。マイルストンは該当する
曜日のセルに自動配置済み。タスクは「割り振り前」列からドラッグ&ドロップで曜日に振り分ける。

```
テーマ     | 割り振り前 | 月        | 火       | 水        | 木     | 金 | 翌週以降
テーマ1    |           |          | マイルストン1 |         |       |    | マイルストン2
           | タスク1    |          |          |          |       |    |
           | タスク2    |          |          |          |       |    |
           | ...       |          |          |          |       |    |
テーマ2    |           |          |          | マイルストン1 |       |    |
           | タスク1    |          |          | タスク2,3,4 | タスク5 |    |
```

## 2. 現行機能との関係（確定: 論点A）

**確定**: 現行の`/tasks/daily-plan`（時間軸カレンダー・GCal連携・capacity管理）はそのまま残し、
本機能は**完全に別の新規route・新規実装**として追加する。

- 新ルート: `/tasks/weekly-plan`（既存`/tasks/daily-plan`とは別route prefix）
- 既存の`daily_task_plans`/`daily_task_plan_items`テーブル・GCal連携・容量管理(`/tasks/capacity`)
  は一切変更しない。新機能は完全に独立した新規テーブルを使う。
- ナビ上の名称: 既存機能は「直近タスク設計」のまま変更しない。新機能は**「週次タスク設計」**
  という別名称にする（同じ名前だと混同するため）。

## 3. データモデル

### 3.1 テーマ＝既存の`link_type`/`link_id`（新規マスタ不要）

既存の`/tasks`看板がすでに持つ分類をそのまま流用する。以下はすべて**既存コード**（新規実装不要、
そのまま呼び出す）:

- **テーマの実体**: (`link_type`,`link_id`)の組（`'delivery'|'deal'|'issue'`＋紐づく
  `deliveries`/`deals`/`deal_issues`のid）。1つの(`link_type`,`link_id`)が1テーマ。
- **訂正（2026-10-06、実装前調査で判明）**: タスク↔テーマは**多対多**。実体は
  `task_entity_links`テーブル（`task_id, link_type, link_id`、sfa_db.py:937-945）で、
  1タスクが複数テーマに同時に紐づき得る（旧`tasks.link_type`/`tasks.link_id`単一カラムは
  レガシーで新規書き込みされない、読み取り後方互換のみ）。既存の`task_link_summary()`は
  「1タスクが複数の紐づけ先を持つ場合、該当する全ての紐づけ先に重複してカウントする
  （ユーザー確定仕様）」と明記されており、**本機能もこの前例を踏襲**する: 複数テーマに
  紐づくタスクは、Output1/Output2の**両方のテーマブロックに重複して表示**する。
  ただし**曜日への配置（割り振り）は1タスクにつき1つ**（`weekly_task_plan_items`は
  task_id単位で1行、day_index/week_offsetもタスク単位の値）。そのためドラッグ&ドロップで
  ある曜日へ動かすと、そのタスクが表示される**全テーマブロックで同時に同じ曜日へ移動した
  ように見える**（UI再描画時に反映）。この挙動は仕様として進める（既存の重複カウント方針との
  整合性を優先）。
- **テーマの表示名**: `sfa_db.task_link_label(con, link_type, link_id)`（sfa_db.py:4758-4793）
  — delivery: `"{account_name}：{title or deal_name}"` / deal: `"{account_name}：{deal_name}"` /
  issue: `deal_issues.issue`のテキストそのもの。
- **大分類**: `sfa_db.task_link_summary(con)`（sfa_db.py:5299-5345）が内部で計算している
  バケット分けをそのまま使う（`cowork/webapp.py:11311-11336`の看板チップ描画ロジックと同じ）。
  - `link_type='delivery'` → "Delivery"
  - `link_type='deal'` → "商談"
  - `link_type='issue'` かつ`deal_issues.deal_id`あり(`has_deal`) → "社内PJ(商談個別)"
  - `link_type='issue'` かつ`deal_issues.company_function`あり → `"社内PJ({company_function})"`
    （`company_function`は`masters`テーブルのkey`"company_functions"`で管理者が自由に追加できる
    マスタ——デフォルトは`["経営企画","総務","法務","人事","財務","経理"]`だが、本番では
    IT/マーケ/営業等が追加済み。ユーザー画面に出す値は常にこのマスタをそのまま参照し、
    本機能側で独自に複製・ハードコードしない）
  - `link_type='issue'`かつ`company_function`未設定 → "社内PJ(商談共通（機能未設定）)"
- **`task_projects`/`tasks.project`は本機能では一切使わない**（別概念、混同しない）。

**実装方針**: 既存の`task_link_summary()`/`task_link_label()`をそのまま呼び、バケット分け
ロジックを複製しない（もし看板側の実装が将来変わった場合も自動的に追従させるため）。
必要であれば、バケットラベル計算部分（webapp.py:11311-11336の`for _lt, _lbl_prefix, ...`
ループ）を`sfa_db.py`側の小さい共通ヘルパーへ切り出し、看板・本機能の両方から呼ぶ形に
リファクタしてもよい（実装時に判断）。

### 3.2 マイルストン（新規テーブル、テーマ＝`link_type`+`link_id`に紐づく）

```sql
CREATE TABLE theme_milestones (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    link_type   TEXT NOT NULL,            -- 'delivery'|'deal'|'issue'（テーマの実体と同じキー）
    link_id     INTEGER NOT NULL,
    due_date    TEXT NOT NULL,            -- YYYY-MM-DD
    title       TEXT NOT NULL,            -- マイルストン名（例: "先方担当者名" "中間報告リスケ"）
    status      TEXT DEFAULT '未達成',     -- '未達成'|'達成'
    created_at  TEXT DEFAULT (datetime('now')),
    updated_at  TEXT DEFAULT (datetime('now'))
);
CREATE INDEX idx_theme_milestones_link ON theme_milestones(link_type, link_id);
```

マイルストンは**テーマに紐づく永続データ**とする。週次プラン作成・編集のたびにゼロから
入力するのではなく、前回までに入力した内容が残った状態で、都度レビュー・追加・編集・削除が
できる（削除可能＝完全な永続マスタではなく、ユーザーが能動的に手入れする「生きたTODOリスト」
に近い）。週次プラン画面では、該当テーマの未達成マイルストンのうち表示期間内(今週の月〜金)に
収まるものはその曜日列へ、期間外のものは「翌週以降」列へ自動配置する。プラン作成/テーマ追加時の
「マイルストン入力」ステップは、空欄フォームではなく**既存マイルストン一覧の確認・編集画面**
として出す（新規追加・既存の編集・削除がその場でできる）。

**期限超過の扱い（確定: 論点E）**: ユーザーはタスク設計のたびに毎回マイルストンを見直し・
更新する運用のため、**期限超過（今週より前の日付のまま未達成）は実運用上発生しない前提**とし、
専用の警告表示・繰り越しロジックは実装しない（シンプルに「日付が今週の月〜金のどこにも
該当しなければ翌週以降列へ」という素朴なロジックのみでよい）。

### 3.3 週次プラン（新規テーブル、既存`daily_task_plans`とは別物）

```sql
CREATE TABLE weekly_task_plans (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    owner       TEXT NOT NULL,            -- 担当者
    label       TEXT,                     -- 表示名（ユーザーが名前を付けて保存。例: "通常業務"）
    week_start  TEXT NOT NULL,            -- その週の月曜日 YYYY-MM-DD（週の切替の基準）
    created_at  TEXT DEFAULT (datetime('now')),
    updated_at  TEXT DEFAULT (datetime('now'))
);
CREATE TABLE weekly_task_plan_items (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    plan_id     INTEGER NOT NULL,         -- weekly_task_plans.id
    task_id     INTEGER NOT NULL,         -- tasks.id
    week_offset INTEGER NOT NULL DEFAULT 0,  -- 0=当該週, 1=翌週, ...（「▶次週」での配置先）
    day_index   INTEGER,                  -- 0=月,1=火,2=水,3=木,4=金, NULL=割り振り前
    sort_order  INTEGER DEFAULT 0,        -- 同一セル内の並び順
    created_at  TEXT DEFAULT (datetime('now'))
);
```

**既存機能との最大の違い（確定: 論点D）**: 現行`daily_task_plans`は「確定するたびに新規
スナップショット行を追記（上書きしない、やり直すと履歴が増える）」設計。本機能は**1つの
`weekly_task_plans`行を継続的に編集し続ける（スナップショットではなく永続オブジェクト）**。
確定操作は「このプランの現在の状態をOutput1/Output2として出力する」という意味であり、
DB上の別履歴は残さない。

### 3.4 タスク側の変更

既存`task_entity_links`（＋`sfa_db.get_task_links`/`set_task_links`）をそのまま使う。
新規カラム・新規テーブル追加は不要。「どのテーマにも紐づかないタスクがあれば、紐づけるように
促す」は、プラン作成/タスク追加時に`get_task_links(con, task_id)`が空のタスクを検出し、
その場で紐づけ先を選ぶモーダルを出す形で実装する。

**UIは完全に既存コンポーネントを再利用する**（新規に作らない）:
- ピッカー本体: `_task_link_picker_html(con, *, prefix, cur_type, cur_id, ...)`（webapp.py:10801〜）
- 複数選択・チップ表示JS: `taskLinkMultiPick(prefix)` / `taskLinkMultiRenderHtml(links)`（共通ヘルパー、
  webapp.py:920-962）。既存のタスク編集フォーム（`prefix="tfLink"`、`#tfLinksList`/`#tfLinksJson`）
  と全く同じ構成でそのまま埋め込む。
- 保存は`sfa_db.set_task_links(con, task_id, links)`をそのまま呼ぶ。

## 4. 画面・操作フロー

### 4.1 新規プラン作成 / 既存プランを開く

- `/tasks/weekly-plan` 一覧（担当者別の既存プラン一覧、「＋新規プラン作成（タスクを選ぶ）」導線）
- 新規作成（2026-10-06実装確定: 「最初のタスクを選ぶUIはすべて直近タスク設計を流用して」の
  ユーザー要望により、別立てのフォーム/モーダルは廃止し、既存の看板ピック機構
  （`/tasks?pick=1`）をモード切替して完全に同一のUIで流用する）:
  1. 一覧ページの導線、または看板画面上部の「🗓️ 週次タスク設計」ナビボタンから
     `/tasks?pick=1&pickmode=weekly` へ遷移。
  2. 担当未選択ならゲートポップアップ（既存`#dpGatePop`、`pickmode`に応じて
     「🗓️ 週次タスク設計」のラベルで表示）で担当を選択。
  3. 看板がチェックボックス選択モードになり（`#taskBoard.picking`）、ピックバーの文言・
     遷移先ボタンも`pickmode`で出し分け（「次へ（ボードへ）」）。
  4. 「次へ（ボードへ）」→ `GET /tasks/weekly-plan/new?assignee=...&picked=id1,id2,...` へ遷移し、
     `weekly_task_plans`行を1つ作成、ピックしたタスクを`weekly_task_plan_items`へ
     （`day_index=NULL`＝割り振り前の状態で）追加 → 日別タスク表画面（ボード）へリダイレクト。
  - 選択タスクに`link_type`/`link_id`が無いもの（どのテーマにも紐づかないタスク）は、
    作成時のモーダルでブロックせず、ボード画面側の警告バナー＋「紐づける」ボタン
    （既存の`/tasks/{id}/edit`へ遷移するだけ）で事後対応する（§4.2参照、作成フローの
    簡素化を優先）。
  - マイルストン入力も作成時のプロンプトにはせず、ボード画面のテーマ行「+マイルストン」
    ボタンから都度追加・編集する（§4.2参照）。

### 4.2 日別タスク表画面（メイン画面）

- 列: テーマ（左端、大分類→テーマ内の並び順は暫定でテーマ表示名の昇順。要実装時確認） /
  割り振り前 / 月〜金（日付併記、例"月 10/6"） / 翌週以降
- 行: テーマごとのブロック（大分類ごとにグループ化、大分類見出し行を挟む）。各ブロック内、
  マイルストンが該当曜日列へ配置され、その下にタスクが曜日別に並ぶ（期限超過の特別処理は
  無し、§3.2参照）。
- ドラッグ&ドロップ: タスクカードを列間で移動（HTML5 drag-and-drop or ライブラリ無しの
  pointer-events実装、既存`daily_plan_page`のJSを参考にできるが時間軸計算は不要になる分
  大幅に簡素化できる）。
- タスク追加（プラン作成後に追加発生時）: 「+タスク追加」ボタン → 既存のタスク作成モーダルを
  流用 → 作成後は自動で「割り振り前」列へ追加。
- テーマ追加: 「+テーマ追加」→ 紐づけ先（Delivery/商談/社内PJ）の選択UI（既存の候補検索等を
  再利用）→ テーマ行が追加される。
- マイルストン追加: テーマ行の「+マイルストン」→ 日付+名称入力 → 該当曜日列へ即配置。
- 割り振り済みタスクを「割り振り前」へ戻す: ドラッグで戻すか、カードの「未割り振りに戻す」操作。
- 「▶次週」: `week_offset`を+1した表示に切り替え。テーマ/マイルストン/「割り振り前」列は
  週をまたいで共通（同じ`weekly_task_plans`行に属する）。次週の列へタスクをドラッグすると
  その`weekly_task_plan_items`行の`week_offset`が更新される。
- タスクカードクリック: フローティング編集パネル表示（既存タスク編集モーダルと同内容—
  ステータス/期限/次アクション/テーマ/工数感等）、その場で更新。完了操作もここから
  （チェック一発 or ステータス変更）。

### 4.3 確定・出力

- 「確定」ボタン → Output1（Slackメモ用テキスト、クリップボードコピー導線）と
  Output2（表のHTML表示）を生成して表示。
- 保存は自動（`weekly_task_plans`を都度更新）のため、確定は「今の状態を出力する」操作であり、
  データの確定/ロックではない（後からいくらでも編集・再出力可能）。

## 5. Output1（Slackメモ）仕様

```
<大分類>
• <テーマ名> - <直近マイルストンの日付(M/D形式)><マイルストン名>
  ◦ <タスク名>
  ◦ <タスク名>
• <テーマ名>（マイルストン無しの場合は日付部分を省略）
  ◦ <タスク名>
```

- 大分類ごとに改行区切り（§3.1のバケット順: Delivery→商談→社内PJ各機能→社内PJ(商談個別)）、
  大分類内はテーマ表示名の昇順（暫定、実装時に見やすい順を再検討してよい）。
- 直近マイルストン＝そのテーマの未達成マイルストンのうち最も日付が近いもの1件のみ表示
  （複数あっても1階層目には直近1件のみ）。
- タスクは**曜日に関わらず、このプランに含まれる全タスク**を列挙する（「割り振り前」のものも
  含む——Output1は「今週やりたい作業の一覧」であり、曜日配置はOutput2の役割のため）。
- 文字はSlackのリッチテキスト箇条書き入力（`• `/`  ◦ `等、実際にSlackへ貼り付けて
  箇条書き認識される具体的な文字コードは実装時に実機検証する）。

## 6. Output2（日別タスク表）仕様

- HTML `<table>`（or CSS Gridベースの表）で生成、既存の各種レポート機能と同じ`render()`
  配下のページとして表示。**画面表示のみ**（ダウンロード機能は無し、確定: 2026-10-06）。
- レイアウト要件（確定: 2026-10-06ユーザー指摘）: **横幅は画面いっぱいに使う**（テーマ列・
  割り振り前列・月〜金・翌週以降の8列をビューポート幅に合わせて配分、横スクロールに
  極力頼らない）。**縦方向も可能な限り1画面に収まるように**し、テーマ数・タスク数が多い
