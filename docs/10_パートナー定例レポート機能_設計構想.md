# 「定例」ページ化 + パートナー定例(週次)機能 設計構想（2026-10-07ドラフト）

関連: [`08_全社定例レポート機能_設計構想.md`](./08_全社定例レポート機能_設計構想.md)（流用元・確定仕様）。
本docは全社定例に対する発展機能であり、全社定例側の確定仕様は変更しない（別途「全社定例の修正」
のみ適用、後述9章）。

## 1. 背景・目的

全社定例（月次、ナビ「全社定例」）は経営向けに運用中。これとは別に、パートナー
（コンサルタント＝マネージャーロール）向けの**週次**定例資料も同じ仕組みで作りたい、という
発展依頼。全社定例の３画面（❶業績推移・❷Pipeline・❸テーマ別状況）のうち、❶はそのまま流用、
❷❸は見せ方を変えて流用、さらに新規の❹生産性ページを追加する。

ナビ構成も変更する: 「全社定例」の単一リンクを「定例」という入口に変え、入口から
「全社定例(月次)」「パートナー定例(週次)」の2択に分岐する。

## 2. 全体設計

### 2-1. ランディングページ

新規ルート `/regular-meeting`（仮）。大きなボタン2つ（全社定例／パートナー定例）を表示し、
クリックで各機能へ遷移するだけの単純なページ。既存 `/monthly-report` は全社定例の実体として
そのまま残す（URLは変えない。ナビの表示ラベルと入口だけを変える）。

- Nav: `("/regular-meeting", "定例")` に変更（旧 `("/monthly-report", "全社定例")` を置換）。
- `ROUTE_ACCESS["/regular-meeting"]` は `/monthly-report` と同じ閲覧ポリシー
  （経営/マネージャー=full、メンバー/事務=view、外部=hidden）を踏襲。
- `/monthly-report`・新設する `/partner-meeting` 系はそれぞれ個別の `ROUTE_ACCESS` を維持
  （入口ページを増やしても既存ルートのアクセス制御は変更しない）。

### 2-2. パートナー定例の位置づけ

- データソースは全社定例と全く同じSFA実データ（別集計・別テーブルの新設は最小限に留める）。
- 編集可能なのは❷のテーマ別状況(Track B相当)のみ。❶❸は全社定例と同様に完全自動（Track A、
  DB保存なし・都度再計算）。
- 権限は全社定例と同じ「閲覧=全社員（外部除く）、編集(Track B)・Fix=経営/マネージャー」を踏襲。

## 3. 画面構成（パートナー定例、4ページ）

ページ番号はユーザー依頼の原文表記に合わせる（1 Pipeline・2 テーマ別状況・3 業績推移・
4 生産性）。タブ切替は全社定例と同じ仕組み（`mrSwitchTab`相当）を流用。

### 3-1. ページ1: Pipeline（Sales / Delivery の2バケットのみ）

全社定例❷は Sales / Closing / Delivery の3バケットだが、パートナー定例は **Sales / Delivery
の2バケットのみ**（Closingは無い）。

**Sales バケット**（2026-10-07実機フィードバックで再確定。取り消し線部分は初版からの変更点）

- 抽出条件（確定）: ~~ステージが「提案」「クロージング」「受注」のいずれか OR 重要度が高/中~~
  **受注済み(stage='受注')は常に対象外**（Deliveryで既に追えているため）。残りを2段組で表示する:
  - **上段**＝「ステージが提案/クロージングのいずれか（提案以上）」OR「重要度が高」
  - **下段**＝「ステージが提案/クロージング未満（初回アポ実施・要件詰め・保留中）」AND
    「重要度が中」
  - どちらにも該当しない商談（提案未満かつ重要度低/未設定）は対象外。
  全社定例の `_delivery_confidence()` ベースの絞り込みとは別ロジック（deals.stage と
  deals.importance の直接判定）。
- 表示項目: ステージ、主担当(owner)、アカウント、案件名、Pipeline金額。
  **Pipeline金額の定義（確定）**: `deals.value_lumpsum`（単発総額）のみ。`value_recurring`・
  `approach_value`は含めない。未入力(NULL)は `na` 表示。
- 並び順（確定）: **上段/下段の段** → `主担当のマスタ順(sfa_db.OWNERS配列順)` →
  `ステージ降順` → `Pipeline金額降順` → `Noの古い順(id昇順)`。
  「ステージ降順」＝受注が最上位（`DEAL_STAGES`インデックス降順。2026-10-07ユーザー確認済み。
  ただし受注は上記の通りSales対象外のため、実際に並ぶのは提案/クロージング/要件詰め/
  初回アポ実施/保留中のみ）。

**Delivery バケット**
- 全社定例❷のDeliveryと同じ表示項目（期間・責任者ワッペン含む、9章で全社定例側にも追加）。
- 並び順（確定・2026-10-07単純化）: ~~主担当のマスタ順 → 開始日新しい順~~ **開始日新しい順
  のみ**（主担当順は入れない。全社定例❷のDelivery並び順と完全に揃える）。
- 「Week1」「開始間近」「終了間近」ワッペン（新規・確定。2026-10-07追加修正）: 当該週(今週の
  月曜起点)がちょうど`start_week`の場合は**「Week1」**を表示（「開始間近」ではない）。
  当該週より後、+2週間以内に`start_week`が来る場合は「開始間近」。`end_week`が当該週〜
  +2週間以内に来る場合は「終了間近」。全社定例❸のDelivery一覧にも遡って適用する
  （9章、ユーザー確定「両方に適用」）。
- ホバーで概要ツールチップ（新規）: 期間(`_mr_fmt_week_range`流用)・体制
  (`sfa_db.list_delivery_assignments`)・報酬総額(`_delivery_fee_grand_total`、webapp.py:4372
  流用)を表示。

### 3-4. ページ4: 生産性ページ（新規）

- Delivery案件を縦に並べたリスト形式。各行に横向きグラフを2本表示:
  - 左: 生産性（当該週時点=実線丸、着地予想=点線丸の2点をつないだドットチャート）。
  - 右: 売上=報酬総額（横棒グラフ、数値ラベル付き）。
- 並び順（確定・モックアップ確認後の追加要望）: **当該週時点の生産性(`productivity[今週]`)降順**。
- 案件名の左に責任者ワッペン表示（確定・追加要望。全社定例❷Deliveryの`.mr-plist-owner`と
  同じ見た目のバッジを流用、`sfa_db.list_delivery_assignments`等から責任者ownerを取得）。
- 生産性チャートに縦の閾値線を表示（確定・追加要望）: `150`=赤字ライン(赤)、`350`=最低目標(橙)、
  `400`=目標(青)、`500`=優良(緑)。0〜1000軸上の固定値（Delivery/案件ごとに変動しない定数）。
  モックアップでは点線の縦線+凡例で表現（`350`と`400`はラベルが近接するため上下2段に
  互い違い配置）。この4値は当面コード内定数（例: `_PARTNER_PRODUCTIVITY_THRESHOLDS`）として
  埋め込む。将来変更可能にする要望が出た場合のみ設定化を検討する（現時点では過剰設計を避ける）。
  **閾値線は行ごとに途切れさせず、Delivery一覧全体を縦に貫通する1本の連続した線として描画する**
  （確定・追加要望。各行のチャート領域内で個別に線を引く実装では行間の余白で線が途切れて見える
  ため、行リスト全体を覆う1枚の絶対配置オーバーレイとして描画し、各行はそのオーバーレイより
  手前（z順で上）にレンダリングしてドット/棒が隠れないようにする）。
  **罠（2026-10-07実機フィードバックで発覚・修正済み）**: 行数が多い（タブの固定高を超える）と
  `.mr-tab-panel .card{overflow:hidden}`により画面に収まらない分の行が物理的に不可視・
  到達不能になり、「生産性に載ってるプロジェクトがPipelineのDeliveryより少ない」ように見える
  不具合があった（データ側の抽出漏れではなく、スクロール領域が無かったことによる表示上の
  クリッピング）。軸目盛・閾値ラベル行・行リストをまとめて`.mr-table-scroll`
  （`flex:1;min-height:0;overflow-y:auto`、❸Track Bと同じクラス）でラップし、カードの
  残り高さ内で内部スクロールできるようにして解消（凡例・脚注はスクロール領域の外側=
  常に表示される固定部分のまま）。
- 生産性の計算ロジック（確定・既存ロジック踏襲）: `sfa_db.delivery_weekly_productivity()`
  （weekly_margin/cum_margin/productivity、`productivity[wk]=round(cum_margin*400/cum_workload,1)`）
  をそのまま使う。呼び出し側で `weeks` を契約終了週(`end_week`)まで延長してから渡す既存パターン
  （webapp.py:7295-7303のDelivery詳細ページ実装）を踏襲し、「当該週時点」=
  `productivity[今週]`、「着地予想」=延長後 `weeks[-1]` 時点の値、とする。
  Hisho側dashboard.htmlには同種のチャートの視覚的先例は無い（確認済み）ため、見た目は
  SFA-CRM内で新規デザインする。
- 売上(報酬総額)は `_delivery_fee_grand_total()`（webapp.py:4372、fixed_total+
  performance_fee計算込み）を流用。
- チャート実装方針: 本リポジトリにChart.js等のライブラリ依存は無い
  （stdlib-onlyの設計方針、`CLAUDE.md`参照）。全社定例❶の積み上げ棒グラフが
  `position:absolute`で一度崩壊した実例があるため、**flexboxベースで自作する**
  （横棒はflex-basis比率、ドットは共通スケールの横軸上に`left:{pct}%`等の最小限の
  絶対位置指定に留める）。

## 4. 新規DB・CRUD（sfa_db.py）

```python
# 新規テーブル（SCHEMAに追記。既存テーブルの改変は無いためPRAGMA foreign_keys考慮は不要）
CREATE TABLE IF NOT EXISTS partner_meeting_reports (
    id                   INTEGER PRIMARY KEY AUTOINCREMENT,
    week_start           TEXT NOT NULL UNIQUE,  -- 当該週の月曜 YYYY-MM-DD
    marketing_comment_html    TEXT NOT NULL DEFAULT '',
    marketing_comment_draft   TEXT NOT NULL DEFAULT '',
    development_comment_html  TEXT NOT NULL DEFAULT '',
    development_comment_draft TEXT NOT NULL DEFAULT '',
    product_comment_html      TEXT NOT NULL DEFAULT '',
    product_comment_draft     TEXT NOT NULL DEFAULT '',
    finance_comment_html      TEXT NOT NULL DEFAULT '',
    finance_comment_draft     TEXT NOT NULL DEFAULT '',
    track_a_snapshot_html TEXT NOT NULL DEFAULT '',
    fixed_at              TEXT,
    fixed_by              TEXT,
    created_at            TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at            TEXT NOT NULL DEFAULT (datetime('now'))
);

PARTNER_MEETING_AREAS = ["marketing", "development", "product", "finance"]
PARTNER_MEETING_COLS = ["comment"]
PARTNER_MEETING_FIELD_KEYS = [f"{a}_{c}" for a in PARTNER_MEETING_AREAS for c in PARTNER_MEETING_COLS]
```

CRUD関数は `monthly_reports` 系（`get_monthly_report`/`create_monthly_report`/
`update_monthly_report_field`/`fix_monthly_report`/`reopen_monthly_report`）と同型で
`partner_meeting_*` 名で実装する（コピー&パラメータ変更。共通化の抽象化は今回はしない
=== 設計方針「3行の重複は早すぎる抽象化より良い」に従う。将来similarな3つ目の定例が
出た時に初めて共通化を検討する）。

## 9-2. 2026-10-07さらに追記: 2点の実機フィードバック

1. **Deliveryのバッジ表示は責任者のみ**: パートナー定例①Pipeline・④生産性のDelivery行に
   「責任者(responsible_owner)」バッジと「主担当(deal_owner)」バッジの2つを出していたが、
   紛らわしいとの指摘で**主担当バッジを削除・責任者バッジのみ**に変更。全社定例❷は元々
   責任者バッジのみだったため、今回の修正でパートナー定例側も仕様が揃った。
2. **案件名クリックでSFA詳細ページへ遷移**: 全社定例❷・パートナー定例①Pipeline・
   パートナー定例④生産性のいずれも、案件名(`.deal`)がただのテキストだったのをリンク化。
   リンク先: Sales（deals直接参照の行。パートナー定例①Pipelineのみ）→`/deal/{id}`、
   Delivery行（全社定例❷の全バケット・パートナー定例①②④のDelivery行）→`/delivery/{id}`
   （`_monthly_report_pipeline_lists()`の3バケットは全てDeliveryベースで構築されている
   ため、全件`/delivery/{id}`でよい）。ダウンロード/Fixスナップショット用の
   `_monthly_report_standalone_html`/`_partner_meeting_standalone_html`側は対象外
   （静止ドキュメントのため変更不要、との判断）。

## 9-3. 2026-10-07さらに追記: 3巡目の実機フィードバック（①Pipeline・④生産性）

1. **ワッペンの横幅を固定しアカウント列を揃える**（①Pipeline）: `_delivery_near_badges_html()`
   の戻り値を常に`<span class="mr-near-slot">...</span>`（固定幅58px、flexアイテム）で
   ラップするよう変更。ワッペンが0個でも1個でも2個でも同じ幅を占有するため、後続の
   アカウント名の開始位置が全行で揃う。全社定例❷・パートナー定例①の両方の呼び出し箇所に
   自動的に反映される（関数の戻り値自体を変えたため、呼び出し側のコード変更は不要）。
2. **アカウント名を追記**（④生産性）: 行の名前欄を1行→2行構成に変更（1行目=責任者バッジ+
   アカウント名(小さい文字)、2行目=案件名リンク）。`_partner_meeting_productivity_rows()`に
   `account_name`フィールドを追加。
3. **開始前の案件は当該週時点の生産性を表示しない**（④生産性）: 開始週が当該週より未来
   （＝まだ売上が立っていない）Deliveryは、アサイン等の都合でたまたま
   `delivery_weekly_productivity()`がwork>0を算出してしまうケースがあっても、
   `current`を明示的にNoneへ強制する。これにより実線丸・当該週↔着地予想の接続線を
   描画せず、着地予想の点線丸のみ表示する。
4. **各丸に生産性の数値ラベルを表示**（④生産性）: 実線丸(当該週時点)・点線丸(着地予想)の
   それぞれの下に数値を表示（丸の位置がクランプ(0〜1000%)されていても、ラベルの数値は
   実際の算出値をそのまま表示する——契約内容次第では0〜1000の軸を超える値になりうるが、
   それ自体は既存の計算ロジックの仕様通りであり補正しない）。
5. **主要な数値表示を約2倍に拡大**（④生産性）: 軸目盛(10px→20px)・閾値ラベル(9px→18px)・
   売上総額の数値(12px→24px)。新設した生産性の数値ラベルも同系統の大きさ(16px)で追加。
6. **縦スクロールしても軸目盛・閾値線が固定表示される**（④生産性）: 軸目盛行・閾値ラベル行を
   スクロール領域(`.mr-table-scroll`)の**外側**（カード内の固定ヘッダー部分）に移動。
   縦の閾値線オーバーレイは、スクロールする行リスト(`.mr-table-scroll`に`position:absolute;
   inset:0`を指定)と同じ領域を覆う**兄弟要素**として`position:absolute;inset:0`で重ね描画する
   （`pointer-events:none`でクリックは妨げない）。これにより行リストだけが内部スクロールし、
   軸目盛・閾値ラベル・縦の閾値線は常に画面上の同じ位置に見える（線自体は1.5px幅の薄い
   点線でドット/数値と重なっても実用上ほぼ視認性に影響しない）。

## 9-5. 2026-10-07 別件調査: Delivery詳細ページ「累計稼働率」が直感と合わない件

ユーザーから「250%の稼働を2週強続けただけで、なぜ累計稼働率が600%にもなるのか・
生産性(190万)が低すぎるのでは」という疑問が上がった。`sfa_db.delivery_weekly_productivity()`
を実データ相当の値で再現して検証した結果、**計算ロジックは既存の設計通り正しく動作しており
バグではない**と判断した（以下、確認した事実）:

- 累計稼働率は`sfa_db.py`のdocstring・UIツールチップいずれにも「稼働率(%週)の累計」と
  明記されている仕様で、1週間あたりの合算稼働率(%)を**人数分・週数ぶん単純加算**する
  （カレンダー時間ではなく「人×週」の消費量を表す指標）。今回のケースは
  中島100%＋山端150%＝合算250%/週を、対象外期間(9/21〜9/23の休暇)により初週が
  0.4倍の有効週数となった上で3週ぶん積算：100(0.4週分)+250(1週)+250(1週)=600。
  実際に`delivery_weekly_productivity()`を同条件で実行し、この600という値を再現済み。
- 生産性＝累計限界利益×400÷累計稼働率＝285万×400÷600＝190万（月100%稼働換算あたりの
  限界利益単価）。この式も再現済みで、285万の利益を「250%稼働で2.4週間＝1.5ヶ月相当の
  人員投入」で割った値として数学的に整合している。
- つまり「600%」という表示は「600%の稼働率(0〜100%の意味)」ではなく「のべ6人週分の
  投入量」を意味しており、短期間に複数人を高稼働で投入するプロジェクトほど数字が
  大きく見えるのは仕様通り。ユーザーの違和感は計算バグではなく、**「%週累計」という
  単位の表示が直感的でない**という表示・ラベリングの問題である可能性が高い。
- 対応方針は未確定（コード変更はしていない）。選択肢としては
  (a) 現状維持（ツールチップの説明で十分とする）、
  (b) 累計稼働率を4で割った「月換算値」（この例なら150%）で表示し直す、
  (c) ラベル文言に「%週」等の単位を常時併記する、などが考えられる。
  次にこの話題が出たら、ユーザーにどの対応を望むか確認してから着手すること
  （Delivery詳細ページの既存UIとパートナー定例④生産性ページの両方に影響する可能性がある
  ため、設計判断としてユーザー確認を挟む）。

### 9-5-2. 続報（別案件での再検証）: 「252万も高すぎる」

ユーザーから「月100%稼働の単価を見るのが一般的。今の生産性は週単位の数値なのか？」という
確認と、別のDelivery（早瀬40%・杉山50%・土屋5%の3名、月額報酬200万/月・約15週）での
「252万も高すぎる」という指摘が続いた。同条件を`delivery_weekly_productivity()`で再現し
702.5万限界利益/1130%週稼働→252.2万という値を再現（実際の627万/995%/252万と近似一致、
入力値の細部は推定のため完全一致ではない）。**生産性の式は既に「月100%稼働換算の単価」を
計算しており（`×400`＝`×100%×4週`が月換算そのもの）、ユーザーが言う定義と一致している。
週単位の数値ではない。** その上で「252万が高すぎる」と感じる根本原因を特定した:

- このDeliveryの合算実稼働率(人数分の週平均)は約70〜85%（1人分=100%に満たない）。
  一方、月額報酬は約200万/月で固定（契約金額は人数や稼働率と無関係に決まっている）。
- 生産性＝総利益 ÷ 総稼働量(100%FTE換算の月数)。合算稼働が1人分(100%)に届いていない
  （＝少人数・低稼働で回している）ため、「100%相当に正規化した単価」は実際の月額報酬
  (200万)よりも**必然的に大きく**計算される（200万を0.8人相当で割ると250万になる、
  という単純な比例計算の帰結）。
- つまりこれも計算バグではなく、**「実稼働が1人分(100%)未満のDeliveryは、正規化後の
  生産性が素の月額報酬より高く表示される」という、月100%正規化という指標の定義そのものに
  内在する性質**。ユーザーの直感（「単価」＝契約の月額報酬そのものに近い数字をイメージ）と、
  現在の指標の定義（「実際に投入した稼働量1人分あたりの利益換算値」）がズレている可能性が高い。
- **未解決の論点（ユーザー確認が必要）**: 現在の「実投入稼働量で正規化する」定義のままで
  よいか、それとも「総利益 ÷ 経過月数」（投入人数を問わず、単純にDelivery全体の月次利益
  ペースを見る）という、より単純で契約の月額報酬に近い値になる定義に変更すべきか。
  後者に変更する場合、`cum_workload`を分母に使う現行ロジックとは別の集計が必要になり、
  Delivery詳細ページの既存プレビュー・パートナー定例④生産性ページの両方の実装に影響する
  ため、次回この話題が出たらどちらの定義を採用するかを明確にユーザーに確認してから着手する。
