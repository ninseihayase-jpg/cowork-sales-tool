# Delivery（受注後・納品）アサイン計画 × 稼働可視化 — 設計ドラフト（#75）

作成: 2026-07-23 / ステータス: 設計中（実装は合意後）

## 目的・スコープ

商談が **提案** に至ったら（＝受注見込みが立った段階で）納品（Delivery）に向けた **アサイン計画** を
組み始め、**受注** で確定する。**全メンバー × 週の稼働予定** を可視化する。今SFAの「🚚 Delivery」が
Google Sheetsへの外部リンク1本だけ（`SALES_SHEET_ID`）になっているのを、**SFA内で一貫したプロセス**に置き換える。

### 確定した前提（ユーザー合意済み）
- **起点＝提案ステージ。** 商談が「提案」に至ったらアサイン計画を組み始める（＝見込みキャパを先に押さえる）。
  「受注」で **確定** に昇格。→ 稼働予定は **見込み（提案段階）** と **確定（受注段階）** を区別して持つ。
- **デモ開発（`dev_projects`＝PoC/デモ・#41の点数系）とは別系統。** これは受注前後〜納品の作業アサイン。
- **単位＝FTE割合(%)**（0.5=半分稼働。1人の上限=100%）。
- **紐付け＝商談(deal)単位。** 提案到達で「Delivery案件」を起票し、商談とセットで扱う。
- **入力・保持＝SFA／全体まとめ表示＝Hisho経営ダッシュボード。**
- **入力はできるだけ容易に。20週分を1マスずつ手打ちするのはNG。**

### 見込み／確定の扱い
- Delivery案件は紐づく商談の **ステージ** を引き継ぎ、稼働予定の「確度」を決める：
  - **提案** → `見込み`（tentative）
  - **受注** → `確定`（committed）
- Hishoの稼働テーブルは既定で「**確定のみ**／**見込み含む**」をトグル。見込みは淡色・確定は濃色で重ねて表示し、
  「受注すると各メンバーがどれだけ埋まるか」を先読みできる。
- 提案が失注/リード戻し等でクローズしたら、その見込みアサインは自動的に集計から外す（deal statusで判定）。

## コアの考え方：「アサインブロック」で入力、週へ展開して集計

20週を手打ちさせないため、入力の最小単位を **1週1マス** ではなく **期間ブロック** にする。

> **アサインブロック** = （メンバー・開始週〜終了週・FTE%）
> 例：「山端 を 第3週〜第10週 まで 50%」→ 8週分を自動生成

- 保持はブロックのまま（コンパクト・編集容易）。**読み出し/集計時に週へ展開**する。
- 特定週だけ調整したい場合は「1週だけのブロック」を追加（重なりは合算）。
- これで「20週手打ち」を回避しつつ、週単位の粒度も担保できる。

## データモデル（SFA・SQLite）

### 1) `deliveries` — 受注商談ごとのDelivery案件（1商談=1件）
| 列 | 型 | 説明 |
|---|---|---|
| id | INTEGER PK | |
| deal_id | INTEGER | 紐づく商談。**UNIQUEにしない**（1商談に複数Delivery可・納品フェーズ分割等） |
| title | TEXT | 納品案件名（既定=商談名） |
| start_week | TEXT | 開始週（月曜 YYYY-MM-DD） |
| end_week | TEXT | 終了週（月曜） |
| status | TEXT | 進行中/完了/保留 |
| overview | TEXT | 概要・納品方針（自由記述） |
| created_at / updated_at | TEXT | |

### 2) `delivery_assignments` — アサインブロック
| 列 | 型 | 説明 |
|---|---|---|
| id | INTEGER PK | |
| delivery_id | INTEGER | FK → deliveries.id（ON DELETE CASCADE） |
| owner | TEXT | メンバー（OWNERS） |
| from_week | TEXT | 開始週（月曜） |
| to_week | TEXT | 終了週（月曜） |
| fte_pct | REAL | 稼働率(%) 0〜100（>100も可・過負荷警告） |
| note | TEXT | 任意メモ（担当領域など） |
| created_at | TEXT | |

- 週の起点は **月曜**（週次レポート・スナップショットと統一）。
- 展開：各ブロックを [from_week, to_week] の各週へ配り、`(owner, week)` で **合算**。

### 3) `base_workload` — ベース工数（人 × 機能 × %）
| 列 | 型 | 説明 |
|---|---|---|
| id | INTEGER PK | |
| owner | TEXT | メンバー（OWNERS） |
| function | TEXT | 機能（営業/管理/採用 等・自由 or 小マスタ） |
| pct | REAL | 恒常稼働率(%)（例: 30） |
| updated_at | TEXT | |
- functionは**自由入力**（固定マスタにしない）。UNIQUE(owner, function)。恒常的なので週によらず一定（将来: 期間指定も検討可）。
- 正本はSFA。SFA編集UI＋Hishoからの書き戻し（`POST /api/base_workload` 認証付き）。

### スキーマ追加の作法（CLAUDE.md厳守）
- `SCHEMA` に `CREATE TABLE IF NOT EXISTS` を追加、`init_db()` は新規テーブルなのでALTER不要。
- `DROP` を伴う作り直しは無い（新規のみ）＝FK CASCADE事故の懸念なし。

## 負荷率は「2系統・完全分離」（ユーザー確定 2026-07-23）

負荷率の計算は **デモ開発** と **Delivery（総合稼働）** で完全に分ける。

### ① デモ開発 負荷率（既存のまま・変更しない）
```
デモ負荷率(週,人) = Σデモ開発点数(週) ÷ weekly_max_points（個人の最大点数）
```
- #41/#42の既存ロジック。Delivery機能では一切いじらない。

### ② Delivery＝総合稼働（100% FTEベース）
すべて **FTE%** で表し、100% と比較する。
```
デモ開発工数(FTE%) = デモ負荷率 × 100 ＝ Σデモ点数 ÷ weekly_max_points × 100
delivery工数(FTE%) = Σ delivery assignment fte_pct（週展開・合算）
ベース工数(FTE%)   = Σ base_workload の %（人×機能×%。例: 早瀬 営業 30%）
────────────────────────────────────────────────
総工数(FTE%,週,人) = デモ開発工数 + delivery工数 + ベース工数
総合負荷率(週,人)  = 総工数 ÷ 100%      # 100%超は過負荷（赤）
```
- デモ開発工数は「その人の最大点数に対する使用率」をそのまま%として総工数に載せる
  （＝デモをフル稼働なら100%、そこにdelivery/baseが乗ると100%超＝過負荷が見える）。
- **Hisho表示**：メンバーごとに **「delivery工数」** と **「総工数（デモ+delivery+ベース）」** を併記。
  総合負荷率＝総工数÷100% で色分け。

### ヒートマップ配色（閾値・ユーザー確定 2026-07-23）
100%超が常態化するため、100%だけでなく **150% も閾値**として捉える。段階配色（目安）：
| 総合負荷率 | 意味 | 色（目安） |
|---|---|---|
| 〜70% | 余力あり | 淡い緑/無色 |
| 70〜100% | 適正 | 緑 |
| 100〜150% | 過負荷（許容内・常態） | 黄〜橙 |
| 150%〜 | 危険（要是正・再配分） | 赤（濃いほど超過大） |
- 閾値（100/150 等）は定数で持ち、後から調整可能にする。150%超は特に強調（濃赤・太字）。

## ベース工数マスタ（人 × 機能 × %）
- 営業・管理・採用など「案件に紐づかない恒常的な稼働」を人ごとに%で持つ（例: `早瀬 × 営業 × 30%`）。
- **SFAでもHishoでも都度パラメータ設定できる**こと（ユーザー要件）。
  - 正本は **SFA**（`base_workload` テーブル）。SFAに編集UI。
  - Hishoダッシュボードにも編集UIを置き、**認証付きの書き戻しエンドポイント（例 `POST /api/base_workload`）**でSFAへ反映。
    → 単一の正本を保ちつつ「両方から編集」を満たす（※SFA→Hishoは既存が読み取り同期のみ。書き戻しは新規）。

## 画面設計

### A) SFA：起票導線（自動）
- 商談が **ステージ=提案** に到達したら **自動でDelivery案件を1件起票**（見込み扱い）。商談画面に
  「**🚚 Delivery/アサイン計画**」導線を出し、そこで編集。1商談に複数Deliveryを追加も可（＋ボタン）。
- **受注** に進むと確度が自動で `確定` に昇格（deal.stageから導出するため昇格は自動）。
- 実装：ステージ更新の処理（`upsert_deal`/ステージ変更ルート）にフックし、提案初到達で未作成なら起票。
  誤操作対策として「自動起票された空Deliveryは、内容未入力なら一覧で目立たせる/削除容易に」。

### B) SFA：Deliveryアサイン編集（1案件）
- 上部：期間（開始週〜終了週）・status・概要。
- **アサインブロック入力**（容易さの肝）：
  - 行を「＋メンバー追加」→ メンバー選択・開始週・終了週・FTE% を1行で入力＝1ブロック。
  - 週はプルダウン（案件期間から候補生成）。FTE%はスライダ or 25/50/75/100のクイックボタン。
  - 下に**プレビュー・グリッド**（メンバー×週）をライブ表示：合算FTE%と過負荷(赤)を即時反映。
- 「1週だけ調整」も同じブロック入力（同一週 from=to）で対応。

### C) SFA：Delivery一覧
- 受注商談のDelivery案件一覧（期間・主要アサイン・status）。旧「🚚 Delivery↗（外部スプシ）」の置換。

### D) Hisho：全社 稼働予定テーブル（可視化の出口）
- 行=メンバー / 列=週（ローリング12〜16週・横スクロール）/ セル=Σ稼働率(%)＋負荷色。
- デモ開発負荷と合算（内訳トグル）。capacity超過は赤、余力は淡色。
- データ源：SFA → Hisho へHTTP同期（新API `/api/delivery_load?token=...` が
  `owner × week → fte_pct/points` の展開済み集計を返す。既存の同期基盤・トークン認証に倣う）。

## 連携（SFA→Hisho）
- 既存の `/api/dev_capacity`・`/api/dev_projects` と同じパターンで、
  **`/api/delivery_load`**（トークン認証）を新設。SFA側で週展開・合算まで済ませ、
  `owner × week` ごとに **見込み(提案)** と **確定(受注)** を分けて返す（クローズ済み非受注は除外）。
- Hisho dashboard.html は fetch して「稼働予定」タブを描画（`INTEGRATION.md` の同期表に追記）。
